# F3.0 npm Publish

**Phase**: v2 / Phase 3 — Release Engineering
**Priority**: High
**Dependencies**: **All Phase 1 features (F1.0–F1.6) must be merged first.** F3.0 is the cut event — it's how 2.0 actually ships. Phase 2 work is not blocking and ships through this same pipeline as later minor releases.

## Goal

Get `ctx-sys@2.0.0` onto npm cleanly, with a release process that's repeatable, automated where it should be, and resistant to publishing broken builds. Treat the 2.0 release as the moment to put the release plumbing on a solid footing — the pipeline F3.0 builds is what every ctx-sys release ships through afterwards.

This feature lands last in the 2.0 timeline. Everything in Phase 1 must be merged, tested, and stable before F3.0 cuts the actual release. Any pre-release cuts (`2.0.0-beta.N`) follow the same rule: published only after the in-scope features they verify are merged.

## Why

ctx-sys is distributed via `npm install -g ctx-sys`. Today the publishing path is implicit — `prepublishOnly` runs build + test, but there's no tagged-release workflow, no CHANGELOG discipline, no separation between `latest` / `next` / `beta` dist-tags, and `dist/` appears to be committed to the repo. A 2.0 release with a breaking schema change is exactly the moment to fix all of this.

## Scope

### 1. Repo hygiene

- **Remove `dist/` from version control.** Generated output doesn't belong in git. Add `dist/` to `.gitignore` if it isn't already. `npm publish` packs from `files` in `package.json`, which already lists `dist`. The build step on publish produces what gets shipped.
- **`.npmignore` audit.** Confirm `package.json#files` is the source of truth and there's no `.npmignore` quietly excluding things from the package. The current `files: ["dist", "README.md", "LICENSE"]` is right; verify nothing's missing (whitepaper PDF? icons? not included today — keep that way).
- **Strip dev artifacts.** `tsconfig.json`, source maps, `*.test.ts` are all out via `files`. Verify the final package size on a dry-run pack.

### 2. CHANGELOG

- Adopt [Keep a Changelog](https://keepachangelog.com) format at `CHANGELOG.md`.
- For 2.0: lead with the breaking changes (F1.0 cut — removed tools, no automatic data migration, users delete `.ctx-sys/` and re-index), then additions, then fixes.
- Going forward: every PR with a user-visible change updates `Unreleased`. Release process moves `Unreleased` → versioned section.
- No auto-generation from commits — the prose is the point.

### 3. Versioning + dist-tags

- 2.0 release: SemVer. Removing tools and dropping v1 schema support is breaking, so 1.x → 2.0 is correct.
- During the 2.0 ramp: publish prereleases as `2.0.0-beta.N` under dist-tag `next`. Users opt in with `npm install -g ctx-sys@next`. `latest` stays at the last stable 1.x until the actual cut.
- After ship: `latest` → 2.0.0. `next` is reserved for the next major in development.

### 4. Release workflow

A GitHub Actions workflow at `.github/workflows/release.yml`:

- **Trigger:** Pushing a tag matching `v2.*` (or `v*-beta.*` for prereleases).
- **Job:**
    1. Checkout, install deps, build, run all tests, lint.
    2. Run the stdio-discipline test from F1.4 (MCP server publishes only valid JSON-RPC).
    3. Run a smoke test: install the just-built tarball into a clean tmp dir, run `ctx-sys --version`, run `ctx-sys init` in a fixture project, run `ctx-sys index` against a tiny corpus (no embeddings — `--no-embed`), assert it exits 0.
    4. Publish to npm via `npm publish --provenance` (so the package has a signed link to the GitHub Actions run that built it).
    5. Create a GitHub Release with the CHANGELOG entry as the body.
- **Auth:** Use a granular npm access token scoped to `ctx-sys` only, stored as `NPM_TOKEN` in repo secrets. Document the rotation cadence (every 6 months).
- **Manual trigger as escape hatch:** `workflow_dispatch` lets a maintainer kick a publish from the Actions tab if needed.

### 5. Pre-publish checks (local)

Document the maintainer checklist in `RELEASING.md`:

- All tests pass on `main`.
- CHANGELOG `Unreleased` is empty (it's been promoted to the version section).
- Local `npm pack --dry-run` shows the expected file list and a sane size (target: < 5 MB tarball; today's `dist/` includes a tree-sitter wasm so it'll be a few MB).
- Tag and push: `git tag v2.0.0 && git push origin v2.0.0`. Workflow takes it from there.
- After: verify `npm view ctx-sys` shows the new version.

### 6. Provenance + supply chain

- `--provenance` flag on `npm publish` (set up in the workflow). Requires `id-token: write` permission.
- Result: the npm page shows the GitHub Actions run that built and signed the tarball — users (and Sigstore-aware tooling) can verify origin.
- Pinned dep audit at release time (`npm audit --omit=dev`).
- No optional postinstall scripts (we don't have any today; keep it that way).

### 7. Beta period

- Cut `2.0.0-beta.1` as soon as F1.0 + F1.4 are merged.
- 2 weeks of beta minimum. The trimmed tool surface and the "delete `.ctx-sys/` and re-index" upgrade story are the highest-risk changes; give them real exposure.
- Tag `2.0.0-rc.1` once no regressions for a week; promote to `2.0.0` after another week of quiet.
- Don't ship `2.0.0` straight from a green CI — there needs to be human signal that beta users used it.

## Out of scope

- Homebrew tap, deb/rpm packages, single-binary builds. npm is the only distribution channel for v2.
- Mirrors (JSR, GitHub Packages). One source of truth — npmjs.org.
- Auto-changelog from commits. The prose discipline matters more than the automation.
- Docs site. ctx-sys's primary documentation surface for v2 is the repo README + the v2 docs tree; a standalone docs site is not in scope for the 2.0 cut.

## Acceptance criteria

- [ ] `dist/` removed from git (`.gitignore` updated).
- [ ] `CHANGELOG.md` exists, with the 2.0.0 entry pre-populated covering F1.0–F1.6 and the F3.0 release-engineering changes themselves.
- [ ] `.github/workflows/release.yml` works end-to-end on a test tag (e.g., `v2.0.0-beta.0`).
- [ ] `RELEASING.md` documents the maintainer process.
- [ ] First beta published under dist-tag `next`.
- [ ] `npm publish --provenance` is verified working (the npm page shows the provenance link).
- [ ] No regressions in `npm install -g ctx-sys@next` on macOS, Linux, and (best-effort) Windows.
