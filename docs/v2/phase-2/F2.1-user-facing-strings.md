# F2.1 User-Facing Strings Audit

**Phase**: v2 / Phase 2 — Better Defaults
**Priority**: Medium
**Dependencies**: F1.0 (removes obsolete error codes from `src/errors.ts` and the `session` / `hooks` CLI subcommands); F1.4 (the canonical `--json` error shape `CtxError` serializes into); F2.0 (introduces new stale-index error paths that should carry hints from day one)

## Goal

Every string a new user sees from ctx-sys — error messages, fix hints, CLI `--help` output — should tell them *what's wrong or what to do next* in concrete, actionable terms. Today coverage is patchy on both surfaces:

- **Error messages.** `OllamaUnavailableError` and `OllamaModelNotFoundError` have great `fix:` hints, but `NotFoundError`, `AlreadyExistsError`, `DatabaseError`, and most CLI input-validation errors throw with no recovery hint at all. Several CLI paths still throw plain `Error` and bypass the structured `CtxError` system entirely.
- **CLI `--help` text.** Every command has a one-line `.description()` and per-option strings, but nothing beyond — no usage examples, no longer-form context, no cross-references between chained commands. New users learn the pipeline by experimentation.

Both surfaces are user-facing string consistency. Picking them up in one audit means the recovery hint you see in an error message (e.g. *"Run ctx-sys doctor"*) matches the help text you see in `ctx-sys doctor --help` once F2.2 ships, no drift.

This is the cheap, high-leverage cousin of F2.2's preflight + diagnostic work: F2.2 prevents bad states from happening silently; F2.1 makes sure that when bad states surface (or a user reaches for `--help` to figure out a command), the strings they read actually help.

## Part A — Error messages and hints

### Process

1. **Enumerate every `throw new CtxError(...)` (and every plain `throw new Error(...)`) site in `src/`.** Bucket by command path (`cli/init.ts`, `cli/index.ts`, `cli/search.ts`, …) and by error code.
2. **Categorise each throw site:**
   - *User-facing failure* — a normal-flow user can hit this. Must have a `fix`.
   - *Invariant / programmer error* — never reachable except via a bug. Doesn't need a `fix`, but should be wrapped in a typed `CtxError` rather than `throw new Error(...)` so it shows up in error telemetry consistently.
   - *Stale* — references commands or behaviour cut by F1.0 (e.g. anything mentioning `session`, `decision`, `hooks impact-report`) or by F2.0 → F2.2 reshuffling (e.g. `ctx-sys status --check` after `ctx-sys doctor` takes over).
3. **Add or rewrite `fix:` where it's missing.** Strip stale references where the workaround has been built into the engine.
4. **Lift the `throw new Error(...)` paths** in `src/cli/*.ts` into typed `CtxError` instances — `INVALID_INPUT` for argument validation, `FILE_NOT_FOUND` for missing inputs, etc. Add codes to `ErrorCode` only as needed.

### Style guide

- **Imperative, second person.** "Run `ctx-sys index`", not "the user should run an index".
- **Reference real commands and flags.** No "complete project initialisation" — say `ctx-sys init`.
- **Concrete command first, escape hatch second, doc link last.** Multi-step recoveries belong in a doc page the hint links to, not in the hint itself.
- **Don't echo the error message.** The hint adds *new* information.
- **No stack traces in user output** unless `--debug`. `CtxError.toUserString()` is the only formatter that hits the terminal in normal use.
- **Match `ProviderHealth.fix` shape from F2.2.** Both surfaces present recovery the same way; users see consistent messaging whether the failure comes from a CLI throw or a preflight check.

### Specific call-outs

- **`OLLAMA_UNAVAILABLE`** — fix currently reads `"Start Ollama with: ollama serve\nOr check your config: ctx-sys status --check"`. Update the second line to point at `ctx-sys doctor` (F2.2) instead of `status --check`. `status --check` stays for backward-compat but `doctor` is the canonical name.
- **`OLLAMA_MODEL_NOT_FOUND`** — good fix already; verify the model name in the message is the one currently resolved from config, not the original argument.
- **`PROJECT_NOT_FOUND`** — no fix today. Add: `"Run \`ctx-sys init\` to initialise this directory, or \`ctx-sys project list\` to see existing projects."`.
- **`ENTITY_NOT_FOUND`** — no fix today. Add: `"Run \`ctx-sys index\` if the project hasn't been indexed yet, or \`ctx-sys entity search <query>\` to find similar entities."`.
- **`PROJECT_EXISTS` / `ENTITY_EXISTS`** — no fix today. Add a `--force` hint where the calling CLI command supports one; otherwise suggest the rename / delete path.
- **`DATABASE_ERROR`** (non-locked) — no fix today. Add: `"Check \`.ctx-sys/db.sqlite\` permissions and free disk, then re-run. \`ctx-sys doctor\` (F2.2) will diagnose."`.
- **`DATABASE_LOCKED`** — already has a fix; tighten wording to mention the `.ctx-sys/yaao-mcp.sock` case explicitly when yaao is the other process holding the lock.
- **`PROVIDER_UNAVAILABLE`** — fix mentions `~/.ctx-sys/config.yaml`; verify the path matches whatever F2.2's provider-shape config writes (per-feature `embeddings.provider` rather than the legacy `providers.openai` block).
- **`EMBEDDING_FAILED`, `OLLAMA_REQUEST_FAILED`, `PARSE_ERROR`, `INVALID_INPUT`, `FILE_NOT_FOUND`** — codes exist in `ErrorCode` but have no concrete `CtxError` subclasses. Either add subclasses with fixes, or document them as internal-only and ensure no CLI path surfaces them raw.
- **`SQLITE_VEC_UNAVAILABLE` (new)** — today this is a silent degradation: [src/db/connection.ts:60-65](../../../src/db/connection.ts#L60-L65) wraps the `sqlite-vec` extension load in a `try/catch` and emits a logger warning if it fails, then ctx-sys keeps running with FTS-only retrieval (no vector search). Promote to a typed `CtxError` with a `fix:` ("vector search disabled — retrieval will be FTS-only; reinstall ctx-sys to retry, or check your platform is supported by sqlite-vec"). Surfaced loudly through `ctx-sys doctor` (see F2.2) so a user can never lose half their retrieval pipeline without knowing.
- **`BETTER_SQLITE3_LOAD_FAILED` (new)** — defensive coverage. If `better-sqlite3` somehow loaded incompletely (e.g., a partially-deleted `node_modules`), today every CLI command throws a generic `Error` deep in the connection layer. Add a typed `CtxError` triggered when the connection constructor catches a load failure; `fix:` should suggest `npm install -g ctx-sys --force` and link to the install troubleshooting doc.
- **Node version drift** — [package.json#engines.node](../../../package.json) is `>=20.0.0`, but the source still references "Node 18+" in places that need updating. Audit catches every user-facing string mentioning "Node 18" and updates to "Node 20" (the README itself was already fixed in a prior commit).
- **F1.0 removals** — `SESSION_NOT_FOUND` is removed from `ErrorCode`. Audit catches anywhere else conversational language slipped in (`session`, `decision`, `memory`, `reflection`, `hooks impact-report`).
- **MCP error shape** — `CtxError.toMcpResponse()` already returns `{ error, code, fix? }`. Verify every tool handler propagates `CtxError` rather than catching and re-throwing as plain `Error`, so the `fix` field reaches the calling agent.

## Part B — CLI `--help` text

### Audit process

1. **Enumerate every `new Command('<name>').description(...)` and `.option(...)` site under [src/cli/](../../../src/cli/)** — about 25 surfaces across the surviving CLI (top-level commands + subcommand groups; the `session` / `hooks` groups are removed by F1.0 and excluded).
2. **For each command, ask:**
   - Does `.description()` say *what it does* in concrete terms — not "(like MCP context_query)" or "Database debugging and maintenance tools"?
   - Does the `--help` output include 1–3 usage examples via `addHelpText('after', ...)`?
   - Are options self-explanatory, or do they assume context (HyDE, `--gate`, `--decompose`)?
   - Does it cross-reference the natural next command in the pipeline?
3. **Add `addHelpText('after', ...)` blocks** to the seven top-level commands and to the most-used subcommands (`embed run`, `summarize run`, `entity list`, `graph query`, `kb create`/`install`).
4. **Tighten terse descriptions** to state what the command does without referencing other tools by name as the primary explanation.

### Help-text style guide

- **Descriptions describe behaviour, not other commands.** Replace "Query assembled context (like MCP context_query)" with a sentence that explains what assembled context is.
- **One-line `.description()`, multi-line `addHelpText('after', ...)`.** The description stays one line so `ctx-sys --help` summary tables don't wrap; the long-form lives in the after-block.
- **Imperative, second person in examples.** Same as Part A.
- **Cross-reference the pipeline.** `init` → `index` → `embed run` → `search` / `context`. Each top-level command's after-block points at the natural next step under a `See also:` line.
- **Mark v2-planned features explicitly.** Where help text needs to mention `ctx-sys setup` or `ctx-sys doctor` (F2.2), prefix with "v2:" to signal they're not yet available. Don't add help text that lies about today's surface.

### Per-command call-outs

**Top-level commands:**

- **`init`** — already prints "Next steps" after running ([init.ts:106-108](../../../src/cli/init.ts#L106-L108)); duplicate the same pointers in `addHelpText('after', ...)` so `--help` users see them too.
- **`index`** — add example invocations covering `--no-doc`, `--no-embed`, `--force`. Note that re-running is incremental by default.
- **`search`** — explain HyDE in a See-also paragraph: what it does (generates a hypothetical answer first, embeds *that*), when it helps (conceptual / synonym-rich queries), what it costs (extra LLM call, needs the `hyde` model pulled — `gemma3:270m` in v2, `gemma3:12b` in v1).
- **`context`** — replace `"Query assembled context (like MCP context_query)"` with `"Retrieve and assemble curated context for a natural-language query, with source attribution and token budgeting."`. HyDE explanation same as `search`.
- **`status`** — note that `--check` runs network probes (Ollama, models) and is slower; default is fast and local-only. Once F2.2 lands, `status --check` is superseded by `ctx-sys doctor` — flag that in the after-block.
- **`serve`** — rewrite the description: `"Start the MCP server for AI assistant integration (spawned by Claude Desktop / Claude Code / Cursor — not run directly by humans)."`. After F1.3 lands, add a note about `--socket <path>` for yaao spawn.
- **`watch`** — add a one-line limitation: "watches the filesystem only; `git checkout` / `git pull` / `git rebase` are not picked up. See F2.0 for the git-aware re-indexing path planned in v2."

**Subcommand groups:**

- **`entity`** — group description fine. `extract-rel` is undocumented in the README; either document it in `--help` or move it under `debug`.
- **`graph`** — group description fine. `link` should warn that manually-created links bypass the relationship-extractor and may be overwritten on re-index.
- **`embed`** — `embed run` should mention it depends on Ollama being reachable (and v2's `ctx-sys setup` script once F2.2 ships).
- **`summarize`** — group description `"LLM-powered entity summarization"` is too terse. Rewrite: `"Generate optional LLM summaries for indexed entities (improves retrieval quality at the cost of one LLM call per entity; opt-in)."` Mention what `summarize providers` lists.
- **`config`** — `config get` / `config set` should show the supported keys in `--help` (or point at the schema doc).
- **`debug`** — `debug query <sql>` needs a "destructive queries will damage the index" warning. `debug export` / `debug import` should mention the file format.
- **`kb`** — `"Knowledge base packaging (.ctx-kb)"` is too terse. Rewrite to explain what a `.ctx-kb` is (a sharable indexed corpus packaged for portability), who creates one (someone with a fully-indexed project wanting to share retrieval-ready data), and who consumes (a teammate or downstream user). Include an example.
- **`instruction`** — **decide before the audit runs.** The `instruction` group ([src/cli/instructions.ts](../../../src/cli/instructions.ts)) is registered but undocumented in the README and not in any v2 doc; it reads like a v1 SaaS-era leftover ("team instructions"). Recommend: cut alongside the F1.0 removals unless there's a real current use case. Track as a follow-up decision; if kept, write proper `--help` for it.

**Global option boilerplate:**

`-p, --project <path>` and `-d, --db <path>` appear on most subcommands with terse descriptions. Move the explanation into a top-level `addHelpText('after', ...)` on the root program (`Global options: -p / -d apply across subcommands; default to the cwd-resolved project and config.database.path.`). Keep the options on individual subcommands (commander doesn't make global options ergonomic) but stop trying to explain them per-command.

**Cross-references:**

For each top-level command, add a `See also:` line in `addHelpText('after', ...)`:

- `init` → `index`
- `index` → `embed run`, `summarize run`, `search`, `context`
- `search` → `context` (when you want assembled context, not just hits)
- `context` → `search` (when you want raw hits)
- `status` → `status --check`, v2's `ctx-sys doctor`
- `serve` → MCP client config in the README
- `watch` → `index` (manual one-shot reindex)

**Consolidating duplicate diagnostic surfaces:**

`status --check` and `debug health` overlap today. v2's F2.2 introduces `ctx-sys doctor` as the canonical replacement. Decide which survives in the help text:

- *Recommended path:* keep `status` as a fast local snapshot (no flag); deprecate `--check` in favour of `doctor` once F2.2 ships; remove `debug health` (or alias it). Help text for the survivors makes the deprecation explicit.
- F2.1's job is to make sure the help text and the `fix:` hints in Part A reference the same canonical command.

## Acceptance criteria

**Part A (errors):**

- [ ] 100% of user-facing `CtxError` throw sites carry a non-empty `fix`.
- [ ] Zero `throw new Error(...)` calls in `src/cli/` — all lifted to typed `CtxError`.
- [ ] Every `fix` passes the Part A style-guide rules above (manual review against a checklist in the PR).
- [ ] No `fix` references a command, flag, or config key that doesn't exist after F1.0 / F2.0 / F2.2 land.
- [ ] `CtxError.toMcpResponse()` outputs the `fix` field for every error reachable from any MCP tool handler.
- [ ] `--debug` flag is the only way to surface a raw stack trace at the CLI; default output is `toUserString()`.

**Part B (CLI help):**

- [ ] Every top-level command has 1–3 usage examples in `addHelpText('after', ...)`.
- [ ] Every command description states *what it does* without referencing another tool by name as the primary explanation.
- [ ] Help text consistently surfaces v2-planned features as "v2: …" not as if they exist today.
- [ ] HyDE is explained in one place (a `Concepts` help-after block, or per-command See-also); not silently referenced.
- [ ] `instruction` group: decided (kept + documented, or cut with the F1.0 removals).
- [ ] `status --check` vs `debug health` vs `ctx-sys doctor` (F2.2): one canonical, the others redirect or are removed; help text consistent across all three.
- [ ] No `--help` output references a command, flag, or config key that doesn't exist after F1.0 / F2.0 / F2.2 land — same staleness check as Part A.

## Tests

- `tests/phase-2/strings/error-hint-coverage.test.ts` — walks every code in the `ErrorCode` union and asserts at least one test fixture produces a non-empty `fix`. Coverage check, not behaviour check.
- `tests/phase-2/strings/no-bare-throws.test.ts` — static check: grep `src/cli/` for `throw new Error(`, fail if any match.
- `tests/phase-2/strings/mcp-fix-propagation.test.ts` — for every registered MCP tool, simulate a failure and assert the response JSON includes a `fix` field when the underlying `CtxError` had one.
- `tests/phase-2/strings/help-examples.test.ts` — for every top-level command, assert `--help` output contains the substring "Examples:" (i.e., `addHelpText('after', ...)` is wired up). Coverage check, not content check.
- `tests/phase-2/strings/stale-references.test.ts` — grep all CLI `--help` output and all `CtxError.fix:` strings for references to removed commands (`session`, `hooks impact-report`, etc.) or wrong Node version ("Node 18"); fail if any match.

## Out of scope

- A typed error-code enum to replace string codes. The string union in `src/errors.ts` is fine; richer typing is post-2.x work.
- Localisation of error messages or help text.
- Restructuring `CtxError` itself (constructor shape, `cause` chain). The interface stays; this is a content audit.
- New error categories or new `ErrorCode` values beyond what's needed to lift bare `throw new Error(...)` calls.
- Interactive help (`ctx-sys help <command>`). `commander`'s native `--help` is enough; no separate `help` command.
- Generated reference docs (man pages, `docs/cli.md`). Possible follow-up; F2.1 stays focused on what `--help` shows and what errors print today.
- Rewriting the README. Already covered in a prior commit.
