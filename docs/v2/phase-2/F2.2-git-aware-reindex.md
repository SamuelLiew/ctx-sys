# F2.2 Git-Aware Re-Indexing

**Phase**: v2 / Phase 2 — Better Defaults
**Priority**: High
**Dependencies**: none (works on top of the existing indexer)

## Goal

The ctx-sys index should track the working tree's actual state. Today `ctx-sys watch` catches file changes but does not catch git operations — `git checkout other-branch`, `git pull`, `git rebase`, `git reset` all leave the index reflecting whatever was on disk before. Retrieval is silently stale until someone notices. F2.2 closes that gap by installing post-* git hooks that flag the index as stale and trigger an incremental re-index in the background.

## Why

This is the single most "feels broken" moment in current ctx-sys usage. A user switches to a feature branch, runs `context_query` from their agent, and gets results from the previous branch's code. The agent doesn't know retrieval is wrong. The user doesn't know retrieval is wrong. The fix is small and the impact on perceived quality is large.

`watch` mode doesn't help here because git operations touch many files atomically — by the time watch debouncing settles, the agent has already issued queries against the stale index. The right signal is git's own lifecycle hooks.

## Important — this is NOT the cut `hooks` feature

F1.0 cut the **pre-commit** `hooks` MCP tool and `ctx-sys hooks` CLI subcommand. Those were about a different problem: producing an "impact report" for a staged change. F2.2 covers **post-checkout / post-merge / post-rewrite** hooks for a different purpose: keeping the index in sync with the working tree.

No MCP tool. No `ctx-sys hooks` subcommand. The hooks are installed by `ctx-sys init` and managed by the existing init / setup flow.

## Design

### Hooks to install

| Hook | Fires when | What ctx-sys does |
| --- | --- | --- |
| `post-checkout` | `git checkout <branch>`, `git checkout <file>`, `git switch` | Trigger incremental re-index |
| `post-merge` | `git merge`, `git pull` (when fast-forward or merge) | Trigger incremental re-index |
| `post-rewrite` | `git rebase`, `git commit --amend` | Trigger incremental re-index |
| `post-applypatch` | Less common but cheap to cover (`git am`, format-patch flow) | Trigger incremental re-index |

The hooks call into a small helper:

```bash
# .git/hooks/post-checkout (and friends)
#!/bin/sh
exec ctx-sys reindex --from-git-hook "$@" </dev/null >/dev/null 2>&1 &
```

Background, fire-and-forget, no terminal output during interactive git ops. Errors get logged to `.ctx-sys/reindex.log`.

### `ctx-sys reindex` subcommand

New internal command (not heavily user-facing):

```bash
ctx-sys reindex [--from-git-hook] [--full]
```

Behavior:

- Compute the diff between the index's last-known commit (stored in DB as `index.head_sha`) and the current `HEAD`.
- If diff is empty: no-op, return immediately.
- If diff is small (under a configurable threshold, default 200 changed files): incremental re-index of just those files.
- If diff is large: mark the index stale (`index.stale = true`) and queue a full re-index. `context_query` and `search` print a one-line warning when the index is stale.
- Update `index.head_sha` on success.

The threshold avoids hammering the user's machine on big pulls (e.g., pulling a week of upstream changes). For those, "background full re-index" runs at low priority.

### Stale signal in retrieval

When `index.stale = true`:

- CLI `search` / `context` commands prepend a one-line notice: `note: index is stale (last indexed at <SHA>, current HEAD <SHA>). Run \`ctx-sys index\` to refresh.`
- MCP `context_query` includes a `stale: true` field in the response payload so agents can choose to mention it.
- `ctx-sys status --json` (F1.4) reports `index.stale` and `index.stale_reason`.

This means even when re-indexing is slow, the agent isn't *silently* working off stale data.

### Hook installation

Installed by `ctx-sys init` as part of the same default-on flow as the `.ctxignore` and MCP wiring (F1.6). Flags:

- `--no-git-hooks` — opt out for this run.
- `--git-hooks` — explicit opt-in (for re-running init on an initialized project to add just the hooks).
- `--git-hooks --force` — overwrite a non-matching existing hook.

Matches yaao F14.2 / ctx-sys F1.6 semantics: same defaults, same flag shape, same conflict handling.

### Coexistence with existing hooks

If the target hook file already exists:

- File is not ours (no `# ctx-sys managed` marker): **leave it alone**, emit a warning recommending the user manually add a one-line call to `ctx-sys reindex --from-git-hook`. Don't append silently — clobbering or modifying existing hook logic is a foot-gun.
- File is ours (has the `# ctx-sys managed` marker on line 1): safe to overwrite on `--force`, no-op when matching.

Sophisticated users who use Husky, lefthook, or `core.hooksPath` to manage hooks centrally: document the one-line invocation they should add. Don't fight existing tooling.

### Worktree behavior (yaao integration)

Important interaction with yaao's per-task worktrees:

- Worktrees share `.git/hooks/` with the main checkout (git's design).
- A hook fired inside `.yaao/worktrees/<run>/<task>/` would trigger re-indexing of the *main checkout's* DB. Wrong.
- F2.2 hooks check `git rev-parse --git-common-dir` and only re-index when invoked from the main checkout — not from a worktree.

This guarantees yaao's worktree-per-task model doesn't cause hammer-the-DB problems.

## Configuration

`.ctx-sys/config.yaml`:

```yaml
git_hooks:
  enabled: true                   # default — installed by ctx-sys init
  reindex_threshold_files: 200    # files changed → switch from incremental to full
  reindex_priority: low           # nice(20) on Unix; quiet by default
```

## Edge cases

- **Bare repos.** Hooks not applicable; skip with a notice.
- **Detached HEAD.** Re-index works (HEAD is still a SHA), just doesn't have a branch name. No special handling needed.
- **Hooks disabled globally** (`core.hooksPath = /dev/null`). Detect and warn during `ctx-sys init`.
- **Reindex while another reindex is running.** Use a lock file (`.ctx-sys/reindex.lock`); second invocation exits immediately. Lock is cleaned up on process exit; stale locks (>10 min old) are reaped.
- **Repo isn't a git repo.** `ctx-sys init` already handles this; hooks step is skipped with a notice.

## CLI surface

- `ctx-sys init [--no-git-hooks] [--git-hooks] [--git-hooks --force]` — install or skip.
- `ctx-sys reindex [--from-git-hook] [--full]` — the worker the hooks invoke; can also be called manually.
- `ctx-sys status` — surfaces `index.stale` and last-known SHA.

No new MCP tool.

## Out of scope

- Pre-commit / pre-push hooks. F1.0 cut those for good reason and this isn't bringing them back.
- Git-server-side hooks (push to remote → re-index a CI mirror). Different problem.
- A central daemon watching `.git/HEAD` directly without using hooks. Hooks are git's intended extension point; bypassing them is brittle.
- Reverse direction (ctx-sys writing back to git in any form). One-way: git → ctx-sys.

## Acceptance criteria

- [ ] `ctx-sys init` installs `post-checkout`, `post-merge`, `post-rewrite`, `post-applypatch` hooks by default.
- [ ] Each hook calls `ctx-sys reindex --from-git-hook` in the background, non-blocking.
- [ ] `ctx-sys reindex` correctly diffs `index.head_sha` against current `HEAD` and re-indexes only changed files for small diffs.
- [ ] Large diffs (over threshold) mark the index stale and queue a full re-index.
- [ ] `context_query` and `search` report stale state when relevant.
- [ ] Invocation from a worktree is a no-op (only the main checkout triggers re-index).
- [ ] Existing non-ctx-sys hooks are not clobbered; a warning surfaces with the recommended one-line addition.
- [ ] `--no-git-hooks` cleanly opts out.
- [ ] Lock file prevents concurrent re-indexes.
- [ ] Integration test: switch branches with diverging content; verify retrieval reflects the new branch within N seconds.
- [ ] Integration test: pull a large diff (>threshold); verify stale flag flips and full re-index completes correctly.
