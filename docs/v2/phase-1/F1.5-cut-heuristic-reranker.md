# F1.5 Cut the Heuristic Reranker

**Phase**: v2 / Phase 1 — Focus & Sharpen
**Priority**: Medium
**Dependencies**: none

## Goal

Remove [src/retrieval/heuristic-reranker.ts](../../../../src/retrieval/heuristic-reranker.ts) from the retrieval pipeline. Retain the [0, 1] score normalization step that currently lives inside it, as a small standalone utility. RRF over vector + FTS + graph remains the final ranking signal.

## Why

The heuristic reranker is a 136-line multiplicative scorer with hand-tuned weights (exact name match, term frequency, stopword filtering, etc.) that runs *after* RRF over the top candidates. It's the wrong shape for the job:

- **Hand-tuned weights drift silently.** Every change to the chunker, embedder, or corpus shifts the right weights — but the weights stay frozen. The reranker drifts from useful → neutral → actively wrong over time and there's no signal flagging the transition.
- **It fights RRF.** RRF is already a reranker: it fuses multiple strategies into a stable joint ranking. Stacking a second reranker on top means the second one *overrides* RRF's fusion when their preferences diverge. When the heuristic gets it right, we win; when it's wrong, we've discarded the better signal.
- **Hardest layer to debug.** When a user complains "why did this come back?", multiplicative composition of hand-tuned signals is the most opaque step in the pipeline. Cutting it removes a major source of "I don't understand why retrieval did that."
- **The LLM reranker exists for the cases where quality > latency.** [src/retrieval/llm-reranker.ts](../../../../src/retrieval/llm-reranker.ts) is the right tool when a real reranker is wanted. The heuristic sits in an awkward middle: too dumb for nuance, too opinionated to be invisible.

## What gets removed

- `src/retrieval/heuristic-reranker.ts` — the file.
- Any call site in [src/retrieval/index.ts](../../../../src/retrieval/index.ts) and [src/retrieval/multi-strategy-search.ts](../../../../src/retrieval/multi-strategy-search.ts) that invokes `HeuristicReranker`.
- Any config knob that toggles the heuristic reranker (likely none, but verify).
- Test files exercising the reranker in isolation.

The LLM reranker stays — it's opt-in and there's no equivalent overlap problem.

## What gets kept — score normalization

The heuristic reranker's last step normalizes all post-rerank scores to `[0, 1]`. That normalization is genuinely useful and unrelated to the hand-tuned weighting: downstream code (context assembly, confidence reporting, the relevance-floor cutoff from v1/F10f.1) expects scores in a consistent range. So we extract it before deleting the file:

- New file: `src/retrieval/score-normalizer.ts` — a tiny module with one function:

  ```ts
  /**
   * Normalize a list of search results so the top score is 1.0 and
   * the bottom is 0.0 (linear scaling). Empty input returns empty.
   * Single-result input returns score 1.0.
   */
  export function normalizeScores<T extends { score: number }>(results: T[]): T[];
  ```

- Called once at the end of [multi-strategy-search.ts](../../../../src/retrieval/multi-strategy-search.ts) after RRF fusion (and after LLM rerank if enabled), before results are handed back.
- Same downstream behavior as today.

## What the pipeline looks like after

```text
query
  ├── vector search        \
  ├── FTS5 search           ── RRF fusion ── normalizeScores ── [optional LLM rerank → normalize]
  └── graph traversal      /
```

Cleaner: three retrieval signals, one fusion, one normalization step, optional LLM rerank for the rare high-quality path.

## Risk and how we'll know

This is the change I'd most want an eval suite for — and v2 explicitly doesn't have one (the eval suite was cut as scope). So:

- **Manual sanity pass.** Before merging, run a set of ~10 queries on ctx-sys's own codebase and a second representative repo. Compare top-5 results before/after by inspection. Look for anything obviously worse (a known-good result drops out of top-5, an obviously-irrelevant result jumps in).
- **Open the door for reintroduction.** If a real user reports regression in retrieval quality after the cut, the LLM reranker is the answer, not bringing the heuristic back. Document this.
- **Belt-and-suspenders config.** Ship one release where `retrieval.heuristic_reranker.enabled` exists as an undocumented config knob, defaulting to `false`. If users hit problems, they can flip it to true temporarily while we figure out the LLM-reranker path for their case. Remove the knob in the next release.

## Acceptance criteria

- [ ] `src/retrieval/heuristic-reranker.ts` deleted.
- [ ] All call sites updated; multi-strategy-search no longer invokes it.
- [ ] `src/retrieval/score-normalizer.ts` exports `normalizeScores`; called at the end of the fusion path and after LLM rerank.
- [ ] Score range [0, 1] preserved for downstream consumers (context assembler, relevance floor).
- [ ] Manual 10-query sanity comparison documented in the PR.
- [ ] CHANGELOG notes the cut as a quality-affecting change.
