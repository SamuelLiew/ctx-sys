# F1.4 MCP Server Polish

**Phase**: v2 / Phase 1 — Focus & Sharpen
**Priority**: High
**Dependencies**: F1.0 (tool descriptions must match the 6-tool surface)

## Goal

Make ctx-sys a clean, composable MCP citizen. Three threads:

- **(A)** Stdio discipline + `--json` contracts everywhere
- **(B)** MCP resources for entities — agents can read an entity by URI instead of going through a tool roundtrip
- **(C)** A consolidated `status` / `inspect` snapshot, exposed both as a CLI command and an MCP tool, with a stable JSON Schema

None of these add a new product surface. All three are improvements to existing functionality, borrowed from patterns yaao already uses well.

---

## A. Stdio discipline + `--json` contracts

### Problem

MCP stdio servers must never write to stdout — that channel is reserved for the JSON-RPC protocol. Any stray `console.log` from a transitive dependency crashes the client. ctx-sys has 28 CLI commands and a serve mode sharing the same process; this is a real exposure surface. Yaao keeps stdio strictly clean — ctx-sys should do the same.

Separately: most CLI commands today emit pretty-printed text. Tools that want to compose with ctx-sys (yaao's `yaao_inspect`, CI scripts, dashboards) either parse that text (fragile) or call MCP (heavy). A first-class `--json` everywhere closes that gap.

### Fix — stdio

- **Audit.** Every code path reachable from `ctx-sys serve` is checked for `console.log` / `process.stdout.write`. All non-JSON-RPC output routed to stderr or a structured logger (`debug` / `pino` / similar).
- **Lint.** Add an ESLint rule banning `console.log` in `src/`. CI fails on violation.
- **Test.** A CI test runs `ctx-sys serve` against a mock MCP client and asserts stdout contains *only* valid JSON-RPC frames over a representative workload (`index`, multiple `context_query` calls, `tools/list`, shutdown). Any non-JSON byte on stdout fails the test.
- **Library noise.** Wrap noisy transitive deps (`better-sqlite3` prepared-statement warnings, `pdf-parse` startup output, tree-sitter wasm init logs) so their output goes to stderr.

### Fix — `--json` contracts

- Every read-only CLI command gets a `--json` flag with a documented schema. Priority order:
    1. `ctx-sys status --json` (used by yaao — see C below)
    2. `ctx-sys search "..." --json`
    3. `ctx-sys context "..." --json`
    4. `ctx-sys entity list --json`, `entity get <id> --json`, `entity stats --json`
    5. `ctx-sys graph stats --json`, `graph query <id> --json`
    6. `ctx-sys embed status --json`
    7. `ctx-sys summarize status --json`
    8. `ctx-sys debug health --json`, `debug inspect --json`
- Schemas published as JSON Schema files under `schema/`:
    - `schema/status.schema.json`
    - `schema/search-result.schema.json`
    - `schema/context-result.schema.json`
    - `schema/entity.schema.json`
    - `schema/graph-stats.schema.json`
    - …etc, one per command output type.
- Versioning rule: schemas are SemVer-locked to the package version. Breaking changes only on major releases.
- A `package.json` `exports` entry surfaces the schemas under `ctx-sys/schema/*` for tooling.

### Acceptance

- [ ] ESLint rule + CI test catch any future stdout writes from `ctx-sys serve`.
- [ ] All 9 listed commands support `--json` with a published JSON Schema.
- [ ] Schemas snapshot-tested against real output.
- [ ] yaao's `mcp-config.ts` can parse `ctx-sys status --json` against the schema without try/catch.

## B. MCP resources for entities

### Problem

The MCP spec has two ways to give agents data: **tools** (call, get a response) and **resources** (read a URI directly). ctx-sys ships only tools. Every time an agent wants to read a specific entity it already knows about — because a previous `context_query` returned it, or because it saw it in a file — the agent has to call `entity.get(id)`, a tool roundtrip with all the ceremony that implies.

Resources are the right primitive for "I know what I want; just give me the bytes." Exposing entities as resources changes the agent's mental model: ctx-sys becomes a *navigable filesystem of code knowledge*, not just a search box.

### Design

#### URI scheme

- `ctx-sys://entity/<id>` — single entity by ID
- `ctx-sys://entity/<id>?include=relationships` — entity + outbound graph edges (optional query)
- `ctx-sys://file/<relative-path>` — synthetic resource: all entities in that file, concatenated with separators
- `ctx-sys://search/<url-encoded-query>` — last-resort, on-demand: results as a resource (preferable to use `context_query` tool for this, but the URI makes it composable)

The first two are the primary path; the others are nice-to-haves and can be deferred.

#### MCP protocol surface

- `resources/list` returns up to N entities, paginated via `cursor`. Returns `{ uri, name, mimeType, description }` per entity. `description` is the existing 1-line summary if present; otherwise a generated stub (`function in src/foo.ts`).
- `resources/read` returns the entity's source content as `text/plain` (or `text/markdown` for doc chunks). For `?include=relationships`, returns JSON with `{ entity: { source, ... }, relationships: [...] }` and `mimeType: application/json`.
- `notifications/resources/list_changed` fires when the index is updated (file added/removed, re-indexed). Same pattern yaao uses for its skill hot-reload — borrow the wiring.

#### Pagination & limits

- `resources/list` default page size: 200 entities. Max: 1000.
- Resources do not replace `context_query` — they're a complement for when the agent has a specific ID. The tools list description for `entity.search` should call this out.

#### Lifecycle

- `resources/list` is computed from the live index, not cached. Cheap (< 50ms for 10k entities).
- `resources/read` for an unknown URI returns standard MCP `resource_not_found` error.

### Migration & compatibility

- Existing `entity` tool stays. Resources are additive.
- MCP server capability advertisement (`capabilities.resources = {}` in the server constructor) is already present in [src/mcp/server.ts](../../../../src/mcp/server.ts#L35) — just needs registration code.

### Acceptance

- [ ] `resources/list` and `resources/read` implemented for `ctx-sys://entity/<id>`.
- [ ] `notifications/resources/list_changed` fires on index update.
- [ ] Reading a non-existent URI returns proper MCP error, not a crash.
- [ ] Integration test: agent does `tools/list` → sees resources capability → `resources/list` → `resources/read` returns expected source.
- [ ] README documents the URI scheme.

## C. `inspect` — one-call snapshot

### Problem

Tools that want a quick "is ctx-sys healthy and ready?" today have to call multiple things: `status` for project info, `embed status` for coverage, `debug health` for diagnostics. Each is a separate process spawn or MCP roundtrip. yaao's `yaao_inspect` is a great pattern — one call, structured snapshot, used by dashboards and other agents.

### Design

#### `ctx-sys status --json` becomes the snapshot

Single command, single schema, single source of truth. Not a separate `inspect` command — folding into `status` keeps the surface tight.

Schema (`schema/status.schema.json`):

```json
{
  "schema_version": "2.0",
  "project": {
    "name": "my-project",
    "root": "/abs/path",
    "config_path": ".ctx-sys/config.yaml"
  },
  "database": {
    "schema_version": 2,
    "path": ".ctx-sys/ctx-sys.db",
    "size_bytes": 12345678
  },
  "index": {
    "entity_count": 4231,
    "file_count": 612,
    "last_indexed_at": "2026-05-20T10:30:00Z",
    "stale": false,
    "stale_reason": null
  },
  "embeddings": {
    "provider": "ollama",
    "model": "mxbai-embed-large:latest",
    "coverage_pct": 100.0,
    "missing_count": 0
  },
  "summaries": {
    "enabled": false,
    "coverage_pct": 0.0
  },
  "graph": {
    "edge_count": 9821,
    "edge_types": { "CONTAINS": 4231, "IMPORTS": 1893, "CALLS": 3201, "EXTENDS": 312, "IMPLEMENTS": 184 }
  },
  "health": {
    "ollama_reachable": true,
    "warnings": [],
    "errors": []
  },
  "tools": {
    "mcp_tools_exposed": 6,
    "resources_supported": true
  }
}
```

`stale` is true if any tracked file's mtime is newer than `last_indexed_at`. `stale_reason` is a short human-readable explanation when stale.

#### CLI surface

- `ctx-sys status` — pretty-printed for humans (current behavior).
- `ctx-sys status --json` — strict JSON, the snapshot above.
- `ctx-sys status --check` — current diagnostic mode, emits human text and a non-zero exit code on errors.
- `ctx-sys status --check --json` — combined: emits JSON snapshot AND uses exit code.

#### MCP exposure

The existing `index.status` MCP action returns the same snapshot when called with no arguments. Document this in the tool description.

#### What this replaces / consolidates

- `embed status` keeps existing CLI use but its JSON output is a subset of `status --json`.
- `summarize status` likewise.
- `debug health` keeps its richer interactive flow but the structured fields are in `status --json` too.

The goal isn't to remove the others — it's to give callers like yaao *one* command they can rely on.

### Acceptance

- [ ] `ctx-sys status --json` emits the documented schema.
- [ ] Schema lives at `schema/status.schema.json` and is exported via `package.json#exports`.
- [ ] `stale` detection works against tracked file mtimes.
- [ ] MCP `index.status` returns the same payload.
- [ ] Snapshot test confirms the schema is stable across two consecutive runs with no changes.
