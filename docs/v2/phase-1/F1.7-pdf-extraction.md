# F1.7 PDF Extraction

**Phase**: v2 / Phase 1 — Focus & Sharpen
**Priority**: Medium
**Dependencies**: F1.6 (provider abstraction — the heavy extractor may run as an external process)

## Goal

Replace ctx-sys's flat-text PDF extraction with a structure-aware extractor that preserves headings, lists, tables, code blocks, and reading order. Today PDFs flow through [src/documents/pdf-parser.ts](../../../../src/documents/pdf-parser.ts) using `pdf-parse` v2, which returns per-page plain text — usable, but it discards exactly the signals that retrieval cares about most.

## Why

PDFs are a common source of project documentation that isn't markdown: design docs, RFCs, vendor specs, research papers cited in comments. The current pipeline indexes them like flat text, which has three concrete failure modes:

1. **Tables get mangled.** Multi-column data flattens into space-separated rows with no structural cue. Queries that should hit a row in a spec table return nothing because the row is buried in noise.
2. **Headings vanish.** PDF visual headings are usually larger font + bold — `pdf-parse` returns the text but drops the structure. So we can't chunk on headings, can't surface section paths, can't use heading text as a stronger retrieval signal.
3. **Reading order is lost on multi-column pages.** Two-column papers flatten into "left-column-paragraph-1, right-column-paragraph-1, left-column-paragraph-2, right-column-paragraph-2…" — gibberish from a retrieval standpoint.

The fix is to convert PDFs to **structured markdown** with a layout-aware extractor, then run them through the existing markdown indexing pipeline. Everything downstream of extraction stays the same.

## Approach — three tiers

Different users have different constraints, so ship the extractor as a pluggable strategy.

### Tier 1: `pdf-parse` (current, fallback)

- What we have today: flat-text per-page extraction.
- Pure JS, no system dependencies, zero install friction.
- Kept as the default when nothing better is available.
- Stays usable for simple PDFs (single column, no tables, no images).

### Tier 2: `pdfjs-extract` or `mupdf` with layout heuristics

- Pure JS / WASM, no Python dependency.
- Better than pdf-parse: groups text by font size / position, can infer headings, handles reading order on multi-column pages.
- Not as good as Tier 3 for tables and figures, but a meaningful step up with no external service.
- Reasonable default if available, falls back to Tier 1 silently.

### Tier 3: Docling (or equivalent)

- [Docling](https://www.docling.ai/) is IBM's structure-aware document parser. PDF → markdown with tables as markdown tables, headings preserved, lists as lists, code blocks as code blocks, optional figure captions.
- Python-based, runs as either a CLI (`docling input.pdf -o output.md`) or a long-lived HTTP service.
- Heaviest setup (Python env, model downloads for the layout model) but highest fidelity.
- Plugged in via the provider abstraction (F1.6): ctx-sys talks to a `docling-service` config block the same way it talks to an embedding provider.

Alternatives in the same tier: `marker-pdf` (similar approach, also Python), `unstructured.io` (broader format support, heavier). Whichever has the best license + maintenance picture at implementation time.

## Design

### Pluggable extractor interface

```ts
// src/documents/pdf-extractor.ts
export interface PdfExtractor {
  name: string;
  /**
   * Convert a PDF buffer to structured markdown.
   * Returns one document; the markdown is fed into the existing
   * markdown-parser + document-chunker pipeline.
   */
  extract(buffer: Buffer, opts?: ExtractOptions): Promise<ExtractedPdf>;
  healthCheck(): Promise<ProviderHealth>;
}

export interface ExtractedPdf {
  markdown: string;
  metadata: { title?: string; author?: string; pageCount: number; ... };
  warnings?: string[];     // e.g. "image on page 3 not OCR'd"
}
```

Same shape as the model providers from F1.6 — consistent `healthCheck` semantics, consistent error messages.

### Config

```yaml
documents:
  pdf:
    extractor: auto             # auto | pdf-parse | pdfjs | docling
    # When extractor: docling
    docling:
      mode: cli                 # cli | http
      cli_path: docling
      # or http
      base_url: http://localhost:8000
      timeout_seconds: 120
```

`auto` resolution order: docling (if configured + healthy) → pdfjs (if installed) → pdf-parse (always). Detected once at startup and printed in `ctx-sys doctor`.

### `ctx-sys setup` integration

F1.6's `setup` command gets a section for PDF extraction:

- If user has Python and wants high-fidelity PDFs: offer to `pip install docling` in a venv and configure it.
- Default: pdfjs if it can be bundled cleanly; otherwise pdf-parse.
- Always make clear that PDFs index either way; the choice affects quality, not coverage.

### Caching

PDFs are slow to re-extract (especially Tier 3). Cache extracted markdown by content hash:

- Cache path: `.ctx-sys/pdf-cache/<sha256>.md` + sidecar `.json` for metadata.
- On index, check hash first; only re-extract on cache miss.
- Cache is content-addressed so it survives file moves and is correct across PDF revisions.
- Versioned by extractor name + version so swapping extractors invalidates correctly.

### Migration

Existing PDFs in projects already indexed with pdf-parse: leave alone unless `ctx-sys index --force`. The current quality is usable; re-extracting everything on upgrade would be expensive and surprising. Document the trade-off.

## Out of scope

- OCR for image-only PDFs. Worth its own pass later if users ask. Docling supports it as an option.
- Equation/LaTeX extraction. Same reasoning.
- Other non-markdown formats (DOCX, ODT, EPUB). Pandoc covers most of this; could be a future extractor implementing the same interface.
- A new MCP tool for PDF extraction. PDFs flow into the normal document index; no new surface.

## Acceptance criteria

- [ ] `PdfExtractor` interface defined; existing pdf-parse logic refactored to implement it.
- [ ] At least one Tier 2 or Tier 3 extractor implemented and tested (recommend Docling via CLI mode first — simplest path).
- [ ] Extractor selection via `documents.pdf.extractor` config, with `auto` default.
- [ ] Cache implemented; re-indexing the same PDF is a no-op on the second run.
- [ ] `ctx-sys doctor` reports which PDF extractor is active and its health.
- [ ] A representative-PDF corpus committed to tests (1 simple, 1 multi-column paper, 1 with tables, 1 with code blocks). Tests assert that headings + table cells appear in the indexed output for Tier 2/3 extractors; flat extraction is tolerated for Tier 1.
- [ ] README "Indexing documents" section updated.
