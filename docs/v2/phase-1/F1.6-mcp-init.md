# F1.6 MCP Init Integration

**Phase**: v2 / Phase 1 — Focus & Sharpen
**Priority**: Medium
**Dependencies**: F1.4 (the tool descriptions / status schema that the registered server will expose)

## Goal

A new user goes from `npm install -g ctx-sys` to "Claude Code / Cursor / Codex can call `ctx-sys` tools" in one command. Today the missing step is hand-editing `.mcp.json` (and per-agent equivalents). `ctx-sys init` should do it.

This feature is designed to match yaao's [F14.2 `yaao init --mcp`](../../../../yaao/docs/phase-14/F14.2-init-mcp.md) — same defaults, same flag shape, same conflict semantics, same per-agent file coverage, same "no standalone subcommand" stance. Users running ctx-sys + yaao together get a consistent experience: both tools land their MCP entries in the same files under different keys, on the same `init` flow.

## Current behavior (verified)

[src/cli/init.ts](../../../../src/cli/init.ts):

- Writes `.ctx-sys/config.yaml` via `ConfigManager.saveProject`.
- (After F1.1) writes a seeded `.ctxignore`.
- Nothing touches `.mcp.json` or any per-agent config.

Project-scoped `.mcp.json` (Claude Code), `.cursor/mcp.json`, and `~/.codex/config.toml` are the standard places agent tools look for MCP server registrations. Today users hand-copy the snippet from the README into each.

## Behavior change

`ctx-sys init` defaults to writing the ctx-sys MCP server registration into the project's `.mcp.json` and per-agent equivalents, alongside whatever else lives there. The semantics mirror yaao's F14.2.

### What gets written

In `.mcp.json` (and structurally equivalent in the other targets):

```json
{
  "mcpServers": {
    "ctx-sys": {
      "command": "ctx-sys",
      "args": ["serve"]
    }
  }
}
```

### Per-target file map

| Target | Path | Format |
| --- | --- | --- |
| Claude Code (project) | `<project>/.mcp.json` | JSON `mcpServers.ctx-sys` |
| Cursor | `<project>/.cursor/mcp.json` | JSON `mcpServers.ctx-sys` |
| Codex | `~/.codex/config.toml` | TOML `[mcp_servers.ctx-sys]` |
| Copilot | `<project>/.github/copilot-instructions.md` | Inline reference (Copilot has weaker MCP coverage; mirrors yaao's fallback approach) |

### Flags

- **default (on):** init writes to all four targets that make sense for the project.
- `--no-mcp` — opt out of all MCP wiring this run.
- `--mcp` — explicitly opt in. Useful for re-running `ctx-sys init` on an already-initialized project that just needs the MCP wiring.
- `--mcp --force` — replace a non-matching existing `ctx-sys` entry in any target. Without `--force`, a mismatch is left untouched with a warning.
- `--mcp-name <name>` — register under a different key (useful when running two indexes side by side, e.g., `ctx-sys-frontend` + `ctx-sys-backend`).

### Conflict resolution (matches yaao F14.2)

For each target:

- **File absent:** create it with just the ctx-sys entry. `0644` permissions, 2-space indent.
- **File present, no `ctx-sys` entry:** merge — add `mcpServers.ctx-sys` (or TOML equivalent) without touching siblings. Preserve key order where possible; otherwise accept stable-sort reformatting.
- **File present, `ctx-sys` entry matches what we'd write:** no-op. Don't even modify mtime.
- **File present, `ctx-sys` entry differs:** **leave it untouched** and emit a warning: *"found existing `ctx-sys` MCP entry in `.mcp.json`; not overwriting — run `ctx-sys init --mcp --force` to replace."*
- **File present, malformed:** error out with the file path and a recovery hint ("Fix the JSON or run `ctx-sys init --no-mcp` to skip.").

### Idempotency

Stricter than "entry exists" — the existing entry must **match what we'd write** for the run to be a no-op. If it matches, do nothing. If it differs, warn (don't overwrite without `--force`). This is exactly yaao's semantics.

## Explicitly NOT shipping a standalone `ctx-sys mcp` subcommand

yaao made a deliberate choice in F14.2 to *not* ship a `yaao mcp register` subcommand:

> "A standalone command would re-fragment the surface. The whole point is that init does it by default."

ctx-sys adopts the same stance. Re-running `ctx-sys init --mcp` is the canonical way to wire (or re-wire) MCP on an existing project — no separate subcommand, no parallel code path, one source of truth. Users running ctx-sys alongside yaao see the same shape on both tools.

(An earlier draft of this doc proposed a `ctx-sys mcp register / unregister / status` subcommand. Cut, to stay aligned with yaao.)

## Claude Desktop (global config) — out of scope

Claude Desktop's config lives at `~/Library/Application Support/Claude/claude_desktop_config.json` (macOS) / `%APPDATA%\Claude\claude_desktop_config.json` (Windows) — *not* in the project. Mutating it from `ctx-sys init` would be surprising:

- It's a user-global file, not project-local.
- Users typically run `init` per project; we shouldn't accrete one entry per project to a global file.
- The standard Claude Desktop workflow is a one-time global registration; tooling to do that is a separate, future concern (not even a follow-up; revisit if real demand surfaces).

So F1.6 covers project-local MCP files (`.mcp.json`, `.cursor/mcp.json`, `.github/copilot-instructions.md`) plus the user-global `~/.codex/config.toml` (Codex's location is global by design — there's no project-local override, so we write to it the same way yaao does).

## Migration

Existing projects that already have a `.mcp.json` aren't modified retroactively — we only touch it on `init`. The release notes mention the new behavior; users who want to retrofit run `ctx-sys init --mcp` from the project root.

## Error handling

- Any target file malformed → exit 1 with the file path, line/column if possible, and a recovery hint.
- File exists but isn't writable → exit 1 with the path and the OS error.
- Race conditions on the read-modify-write are acceptable risk — users running `init` aren't simultaneously editing these files. No file locking.

## Acceptance criteria (mirrors yaao F14.2)

- [ ] `ctx-sys init` in an empty repo produces a `.mcp.json` with a valid `ctx-sys` entry; Claude Code opening that repo lists `ctx-sys` tools without any further configuration.
- [ ] `ctx-sys init` in a repo with a pre-existing `.mcp.json` containing other MCP servers preserves them.
- [ ] `ctx-sys init --no-mcp` skips MCP registration entirely.
- [ ] A second `ctx-sys init --mcp` in the same repo is a no-op when the existing `ctx-sys` entry matches what we'd write.
- [ ] A non-matching existing `ctx-sys` entry is left alone with a warning; `--force` replaces it.
- [ ] Per-agent targets (`.cursor/mcp.json`, `~/.codex/config.toml`, `.github/copilot-instructions.md`) are written / merged with the same semantics.
- [ ] Malformed target file produces a clear error, not a crash.
