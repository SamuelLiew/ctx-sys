# F1.6 MCP Init Integration

**Phase**: v2 / Phase 1 — Focus & Sharpen
**Priority**: Medium
**Dependencies**: F1.4 (the tool descriptions / status schema that the registered server will expose)

## Goal

`ctx-sys init` should leave the user with a working MCP wiring in their project — not just a `.ctx-sys/config.yaml` and a `.ctxignore`. Today, after `init`, users have to manually copy a JSON snippet from the README into `.mcp.json` (or their editor's equivalent). That's friction we can remove with one flag, default on.

## Current behavior (verified)

[src/cli/init.ts](../../../../src/cli/init.ts):

- Writes `.ctx-sys/config.yaml` via `ConfigManager.saveProject`.
- (After F1.1) writes a seeded `.ctxignore`.
- Nothing touches `.mcp.json`.

Project-scoped `.mcp.json` is the standard MCP client config (Claude Code, several other clients). The standard shape is:

```json
{
  "mcpServers": {
    "ctx-sys": {
      "command": "ctx-sys",
      "args": ["serve"]
    }
  }
}
```

We have one of these in this very repo as a reference.

## Behavior change

### `ctx-sys init --mcp` (default ON)

After writing config + ignore, init checks for `<project>/.mcp.json`:

- **Not present:** create it with just the `ctx-sys` entry shown above. Permissions `0644`.
- **Present, no `ctx-sys` entry:** parse, add the entry, write back. Preserve all existing keys, key order where possible (JSON5 / preserved-order parser if needed; otherwise sort alphabetically and accept the reformatting). Run through `JSON.stringify` with 2-space indent to keep diffs sane.
- **Present, `ctx-sys` entry already there:** leave it alone. Print a notice: *".mcp.json already registers ctx-sys — no changes."*
- **Present, but malformed JSON:** error out with a clear message; do not overwrite.

### Flags

- `--no-mcp` — opt out for this run.
- `--mcp-name <name>` — register under a different name (useful if a user wants `ctx-sys-frontend` and `ctx-sys-backend` for two indexes).
- `--mcp-target <path>` — write to a non-default location (e.g., a workspace-level config path for a multi-package monorepo).

### Idempotency

Running `init --mcp` twice on the same project should be a no-op on the second run (same content, no edit). Verified by snapshot test.

## What about Claude Desktop and other clients?

Claude Desktop's config lives at `~/Library/Application Support/Claude/claude_desktop_config.json` (macOS) / `%APPDATA%\Claude\claude_desktop_config.json` (Windows) — *not* in the project. Mutating it from `ctx-sys init` would be surprising:

- It's a user-global file, not project-local.
- Users typically run `init` per project; we shouldn't add one entry per project to a global file.
- The standard MCP workflow for Claude Desktop is a one-time global registration.

So F1.6 covers project-scoped `.mcp.json` only. For Claude Desktop, the right tool is a separate one-shot:

```bash
ctx-sys mcp register --target claude-desktop
```

This is **out of scope for F1.6** — file a follow-up. The init command is purely project-local.

### `ctx-sys mcp` subcommand (small, ships with F1.6)

Even though Claude Desktop is out of scope, it's worth pulling the MCP-config logic out of `init` into a reusable subcommand:

- `ctx-sys mcp register [--target project|claude-desktop|...] [--name ctx-sys] [--path <file>]` — add the entry.
- `ctx-sys mcp unregister [--target ...] [--name ctx-sys]` — remove it.
- `ctx-sys mcp status [--target ...]` — show where ctx-sys is currently registered.

`init --mcp` calls into the same code path as `mcp register --target project`. Single source of truth.

## Migration

Existing projects that already have a `.mcp.json` won't be modified retroactively (we only touch it on `init`, and users have already initialized). The release notes mention the new behavior; the `ctx-sys mcp register` subcommand handles retrofitting.

## Error handling

- `.mcp.json` malformed → exit 1 with the file path, line number, and a suggestion: "Fix the JSON or run `ctx-sys init --no-mcp` to skip MCP registration."
- File exists but isn't writable → exit 1 with the path and the OS error.
- Race conditions (someone editing `.mcp.json` while we're writing) → file-lock around the read-modify-write or accept clobber risk; the latter is fine since users running `init` aren't simultaneously editing.

## Acceptance criteria

- [ ] `ctx-sys init` creates or appends to `<project>/.mcp.json` by default.
- [ ] `--no-mcp` flag suppresses it.
- [ ] Re-running `init` is idempotent (no-op when entry already exists).
- [ ] Malformed `.mcp.json` produces a clear error, not a crash.
- [ ] `ctx-sys mcp register / unregister / status` subcommands exist and share code with init.
- [ ] README "Quick Start" reflects the simplified flow: `ctx-sys init` is the only command needed for project-local MCP wiring.
- [ ] Integration test covers: fresh init, init on a project with an existing `.mcp.json`, init on a project with `ctx-sys` already registered, init with `--no-mcp`.
