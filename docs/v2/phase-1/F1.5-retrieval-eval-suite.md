# F1.5 Retrieval Eval Suite

**Phase**: v2 / Phase 1 — Focus & Sharpen
**Priority**: High
**Dependencies**: none (but gates F1.0 / F1.2 / F1.4 quality claims)

## Goal

A regression harness that measures retrieval quality on a fixed corpus + fixed query set. It runs in CI on every change to retrieval-adjacent code (chunker, embeddings, reranker, RRF weights, HyDE) and fails the build on regression. ctx-sys's whole value proposition is retrieval quality — we should not be making changes blind.

## Why

Phase 1 (v2) touches a lot of retrieval-adjacent code: F1.0 drops conversation-flavored entities (changes the corpus); F1.2 swaps default models (changes embeddings and HyDE expansions); F1.4 introduces resources (new code paths). Without a quality harness, every one of those changes is a coin flip on whether retrieval got better or worse — and "feels fine when I tried it" is not a control.

v1's [F10.14 embedding-quality](../../v1/phase-10/F10.14-embedding-quality.md) covered embedding tuning but (verify) doesn't appear to be a CI-gated harness. F1.5 turns it (or a sibling) into one.

## Design

### Corpus

Two fixed corpora:

1. **`tests/eval-corpus/synthetic/`** — a small, hand-curated corpus (~50 files across TypeScript, Python, Rust) with known structure. Designed so we know the ground-truth answer to each query. Lives in the repo; deterministic; runs in seconds.
2. **`tests/eval-corpus/realistic/`** — a snapshot of ctx-sys's own codebase, indexed at a pinned commit. Larger, noisier, closer to user reality. Re-pinned manually when ctx-sys's own structure changes meaningfully.

Both indexed with stock defaults (mxbai-embed-large + gemma3:270m for HyDE/summary per F1.2).

### Queries & ground truth

`tests/eval-corpus/queries.yaml` per corpus:

```yaml
- id: synthetic-001
  query: "where does authentication happen"
  expected_entities:
    - "src/auth/middleware.ts:authenticate"
    - "src/auth/middleware.ts:AuthMiddleware"
  expected_files:
    - "src/auth/middleware.ts"
  must_not_return:
    - "tests/auth/fixtures.ts"

- id: synthetic-002
  query: "retry logic for network failures"
  expected_entities:
    - "src/net/retry.ts:withRetry"
  ...
```

~30 queries per corpus to start. Each query specifies:

- `expected_entities` — list of entity IDs that should appear in results (any order)
- `expected_files` — file-level fallback
- `must_not_return` — anti-examples (false positives we've burned on before)

### Metrics

Per query:

- **Hit@K** — did any expected entity appear in top-K? (K = 1, 3, 5, 10)
- **MRR** — mean reciprocal rank of first expected entity
- **Recall@10** — fraction of expected entities in top-10
- **FP@10** — count of `must_not_return` entries in top-10

Aggregate across the query set:

- Average MRR
- Average Hit@5
- Average Recall@10
- Sum of FP@10 (lower is better)

### Variants

Run the suite across configuration variants to detect which knob a regression came from:

- `--variant default` — vector + FTS + graph + RRF (the shipping default)
- `--variant vector-only` — pure semantic
- `--variant fts-only` — pure keyword
- `--variant hyde` — with HyDE enabled
- `--variant no-rerank` — RRF only, no heuristic rerank pass

This is what F1.5 will eventually let us answer the "should we cut the heuristic reranker?" question with data instead of vibes.

### CI integration

- New script: `npm run eval` runs the synthetic corpus, prints metrics, exits 0/1 based on thresholds.
- Thresholds live in `tests/eval-corpus/thresholds.json`. Initial values pinned to whatever the suite measures on `main`. PRs that improve metrics may update thresholds; PRs that regress must explicitly bump (and explain why) or be rejected.
- Synthetic corpus runs on every PR (fast). Realistic corpus runs on `main` and nightly (slower; needs Ollama).
- Output: a markdown summary commented on the PR showing per-query deltas vs baseline.

### CLI surface

```bash
ctx-sys eval run [--corpus synthetic|realistic] [--variant default|...] [--baseline <path>] [--json]
ctx-sys eval diff <baseline.json> <current.json>     # human-readable diff
```

`ctx-sys eval` is a debug subcommand — not part of the user-facing CLI surface. Not exposed via MCP.

## Threshold philosophy

- **Thresholds are floors, not goals.** They prevent regression. They do not direct work.
- **Improvements should be challenged.** A change that moves MRR from 0.62 to 0.78 might be: (a) genuinely better, (b) overfitting to the query set, (c) gaming a metric the user doesn't care about. Eval is a signal, not a verdict — code review still applies.
- **Add new queries when bugs surface.** Every retrieval bug a user reports becomes a query in the suite. The corpus grows over time and so does our confidence.

## What this enables

Once F1.5 is in place, several deferred questions become answerable:

- **Cut the heuristic reranker?** Compare `--variant default` vs `--variant no-rerank`. If MRR is within noise, drop the reranker.
- **Is `gemma3:270m` actually fine for HyDE?** Compare `--variant hyde` with `270m` vs `12b` (pull both temporarily). Confirm or refute F1.2's claim.
- **Did the F1.0 schema change hurt anything?** Run pre- and post-F1.0 against the same realistic corpus; expect deltas to be near-zero (the cut is conversation data, not code).
- **Is the new chunker change worth it?** Same pattern — run before/after.

## Acceptance criteria

- [ ] Synthetic corpus committed under `tests/eval-corpus/synthetic/` with 30+ queries and ground truth.
- [ ] Realistic corpus pinned to a ctx-sys commit, query set committed alongside.
- [ ] `npm run eval` runs the synthetic suite in < 30s on a developer laptop with stock defaults.
- [ ] CI gate: PRs that regress synthetic-corpus metrics below threshold fail.
- [ ] Metrics: Hit@K, MRR, Recall@10, FP@10 — all reported.
- [ ] At least 3 variants supported: `default`, `no-rerank`, `hyde`.
- [ ] `ctx-sys eval diff` produces a human-readable per-query delta report.
- [ ] README "Contributing" section documents how to add a query and update thresholds.
