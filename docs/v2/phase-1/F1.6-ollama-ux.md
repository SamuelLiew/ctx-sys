# F1.6 Ollama UX

**Phase**: v2 / Phase 1 — Focus & Sharpen
**Priority**: High
**Dependencies**: F1.2 (default models referenced in error messages)

## Goal

Make the first-time Ollama experience clear and actionable. Today, when something is wrong with the Ollama side of the stack, ctx-sys surfaces low-level errors like `fetch failed`, `404 Not Found`, or `ECONNREFUSED` — leaving the user to guess what's broken. This is the single biggest "ctx-sys feels broken" failure mode for new users. None of the underlying causes are hard to diagnose; we just have to detect them and say the right thing.

## Why

The first 60 seconds of using a new tool decide whether someone keeps using it. With ctx-sys, those 60 seconds are usually:

1. `npm install -g ctx-sys`
2. `ctx-sys init && ctx-sys index`
3. Stack trace ending in `fetch failed: ECONNREFUSED 127.0.0.1:11434`
4. User googles, gives up, or finds the README on the third pass

Each of those errors maps to exactly one of ~5 problems:

| Symptom | Cause | Right answer |
| --- | --- | --- |
| `ECONNREFUSED 127.0.0.1:11434` | Ollama not running | `ollama serve` |
| `404 Not Found` on `/api/embeddings` | Embed model not pulled | `ollama pull mxbai-embed-large:latest` |
| `404 Not Found` on `/api/generate` | HyDE/summary model not pulled | `ollama pull gemma3:270m` (only if those features are enabled) |
| `model 'X' not found` | Configured model doesn't exist locally | Pull it or change config |
| Timeout / slow first call | Ollama loading model for the first time | "Loading mxbai-embed-large (first run, ~1 minute)…" |
| All Ollama checks pass, but config points to OpenAI without an API key | Misconfigured provider | "embeddings.provider is openai but OPENAI_API_KEY is not set" |

Each of these deserves a single-line, actionable message. None of them should ever show a raw stack trace to a first-time user.

## Design

### Preflight check on every Ollama-touching command

When `ctx-sys index`, `ctx-sys search`, `ctx-sys context`, `ctx-sys embed run`, or `ctx-sys serve` starts, and Ollama is the configured provider, run a fast preflight:

1. `GET http://<base_url>/api/tags` with a 2-second timeout.
   - **Connection refused?** Print:
     ```text
     Ollama is not reachable at http://localhost:11434.
       Start it with: ollama serve
       Or change provider in .ctx-sys/config.yaml (embeddings.provider: openai)
     ```
   - **Timeout?** Print: `Ollama is slow to respond at http://localhost:11434 (>2s on /api/tags). It may be loading; retry in a moment.`
2. Check the embed model from config is in `/api/tags`.
   - **Missing?** Print:
     ```text
     Embedding model 'mxbai-embed-large:latest' is not pulled.
       Pull it: ollama pull mxbai-embed-large:latest
       Or set embeddings.model in .ctx-sys/config.yaml to a model you have.
     ```
3. If `summarization.enabled` or `hyde.enabled` is true, repeat for those models.

If all checks pass, proceed silently. If any fail, exit `1` with the message.

### Loading-state indicator on first call

The very first embedding request after Ollama starts can take 30-60s as Ollama loads the model. Today this looks like a hang. Detect it:

- If a `POST /api/embeddings` call hasn't returned in 3 seconds, print:
  ```text
  Loading model 'mxbai-embed-large' (first call, this can take ~1 minute)…
  ```
- Spinner / dot progress until the call returns.
- On subsequent calls (assume cached after first response), skip the message.

This is purely cosmetic but it's the difference between "ctx-sys is broken" and "ctx-sys is doing the right thing, I just need to wait."

### Provider misconfiguration

When `embeddings.provider: openai` but `OPENAI_API_KEY` is unset in env and `providers.openai.api_key` isn't filled in:

```text
embeddings.provider is 'openai' but no API key found.
  Set OPENAI_API_KEY in your environment, or set providers.openai.api_key in ~/.ctx-sys/config.yaml.
  Or switch to local: embeddings.provider: ollama in .ctx-sys/config.yaml.
```

Same shape for any future provider.

### `ctx-sys doctor` command (consolidated)

There may already be a `ctx-sys doctor` or `debug health` command — verify and consolidate. After F1.6, `ctx-sys doctor` should:

- Run all preflight checks listed above.
- Print a colored pass/fail per check.
- On failure, print the corresponding actionable message.
- Exit non-zero on any failure.
- Support `--json` for tooling (per F1.4).

This becomes the canonical "is my setup right?" command users are pointed to in any error message.

### Error message guidelines

Apply broadly, not just Ollama:

- **One line of what's wrong** — concrete, not abstract. "Ollama not reachable" not "provider failed."
- **One line of how to fix it** — copy-pasteable shell command if possible.
- **One line of escape hatch** — a config knob to bypass the issue (e.g., switch provider).
- **No stack traces** unless `--debug` is set.

Add a small `formatUserFacingError(err)` helper in `src/cli/error-handler.ts` that consumes structured error codes and emits this shape consistently. Any error not yet structured shows the raw stack trace + a note: "this is an unexpected error; please report it at <issues url>".

## Out of scope

- Auto-pulling models. Tempting but dangerous (large downloads, network policy). Always tell the user, never act on their behalf.
- Bundling Ollama. Distribution complexity for a feature users mostly already have installed.
- Cloud-fallback when local fails. Confusing semantics; better to be explicit.

## Acceptance criteria

- [ ] Preflight runs on `index`, `search`, `context`, `embed run`, `serve` startup.
- [ ] Each of the 5 documented failure modes produces a one-screen, actionable message — no stack traces.
- [ ] First-call loading indicator implemented; gone after the model is warm.
- [ ] `ctx-sys doctor` covers all preflight checks and supports `--json`.
- [ ] All Ollama-touching code paths route through `formatUserFacingError`.
- [ ] Integration test: an Ollama-not-running scenario produces the expected message and exit code, no stack trace.
- [ ] README "Troubleshooting" section enumerates the 5 messages and how to recover.
